# Packaging

Windows, macOS and Linux packages are all built by GitHub Actions: Windows by
[`windows.yml`](../.github/workflows/windows.yml) (below), macOS and Linux see
[macOS](#macos) and [Linux](#linux) at the end.

## Windows

BigWave Radio is packaged the same way as
[ChipWave Studio](https://github.com/postmanpat-303/ChipWaveStudio)
(`installer/chipwave.nsi` + `scripts/package-windows.sh`): an **NSIS** setup and a
portable zip.

The exe is now built with Microsoft's toolchain (`x86_64-pc-windows-msvc`,
`RUSTFLAGS=-C target-feature=+crt-static`) on `windows-latest`. 0.9.6 and earlier were
cross-built on Linux with llvm-mingw (`x86_64-pc-windows-gnullvm`) and needed
`libunwind.dll` next to the exe; that unusual toolchain/DLL combination, together with
the exe being unsigned and new, got it flagged by Microsoft Defender as a false positive.
The MSVC exe needs no DLLs beyond Windows' own.

`crates/bwr-app/build.rs` (winresource, `rc.exe` from the Windows SDK) embeds:
- the wolf icon `assets/bigwave.ico`
- version info: CompanyName `Del (postmanpat)`, ProductName `BigWave Radio`, version = Cargo version
- the manifest `crates/bwr-app/bigwave.exe.manifest`: `asInvoker`, Windows 10/11
  `supportedOS`, PerMonitorV2 DPI awareness, Common Controls v6

## Build

CI: run the **Windows** workflow (Actions tab, *Run workflow*, version optional) or push a
`v*` tag. It runs the tests, `scripts/package-windows.sh`, then verifies the result:
- `dumpbin /dependents`: only Windows system DLLs; the job **fails** if `libunwind`,
  `vcruntime`, `msvcp`, `ucrtbase`/`api-ms-win-crt-*` or any MinGW runtime is referenced
- `mt.exe -inputresource`: the manifest is embedded (asInvoker, PerMonitorV2, Common Controls)
- the icon and version resources are present
- `BigWaveRadio.exe --version` and `--check-plugin` on every bundled plugin
- the zip contents and a silent install / uninstall of the setup exe

The outputs are uploaded as a **workflow artifact only**; the workflow never touches a
GitHub release, so assets are published by hand after review.

Locally (Git Bash on Windows with VS Build Tools, Python and NSIS):

```bash
scripts/package-windows.sh 0.9.8      # version must match [workspace.package] in Cargo.toml
```

Output (`dist/` is git-ignored apart from `dist/README.txt`):

| File | What |
|---|---|
| `dist/BigWaveRadio-<ver>-setup-x64.exe` | NSIS installer |
| `dist/BigWaveRadio-<ver>-windows-x64.zip` | portable: `BigWaveRadio.exe`, `README.txt`, `LICENSE.txt`, `THIRD_PARTY_LICENSES.txt` |
| `dist/SHA256SUMS-windows.txt` | `sha256sum` lines for the two files above (merge into the release's `SHA256SUMS.txt`) |
| `dist/pkg/` | staging folder both are built from |

`bwr-plugin-check-linux-x64` (`cargo build --release -p bwr-plugins --bin bwr-plugin-check`)
is attached to every release as well: the
[plugin hub](https://github.com/postmanpat-303/BigWaveRadio-Plugins) catalog workflow
downloads it from the latest release.

## Installer (`installer/bigwave.nsi`)

Mirrors ChipWave's script:
- installs for all users to `C:\Program Files\BigWave Radio` (admin, 64-bit only)
- Start Menu folder `BigWave Radio` (app + uninstaller), desktop shortcut component
  (on by default, also with `/S`)
- Apps & features entry `HKLM\...\Uninstall\BigWaveRadio`, `DisplayIcon` = the exe's
  own icon, quiet uninstall string, version info on the setup exe
- licence page (`LICENSE.txt`), finish page "Start BigWave Radio"
- silent install: `BigWaveRadio-<ver>-setup-x64.exe /S`
- no file associations, MSI or checksums (ChipWave ships none either)

BigWave-specific additions:
- **Wolf branding:** `installer/welcome.bmp` (164x314) and `installer/header.bmp`
  (150x57), generated by `scripts/make_branding.py`. ChipWave uses the stock NSIS
  bitmaps.
- **Closes a running BigWave** (it lives in the tray) before replacing files,
  found by a Toolhelp process scan.
- **Upgrade from 0.9.3 and older** (Inno Setup, per-user, `%LOCALAPPDATA%\Programs\BigWaveRadio`):
  runs the old uninstaller silently, then deletes anything left behind and the old
  per-user shortcuts, so no stale exe or shortcut with the old icon remains. The
  user's data in `%LOCALAPPDATA%\BigWaveRadio` is not touched.
- **Icon refresh:** shortcuts are deleted and recreated on every install, take their
  icon from the exe resource, and the installer calls
  `SHChangeNotify(SHCNE_ASSOCCHANGED)` so Explorer drops cached icons.
  ChipWave does none of this.

## Icons

| Where | Source |
|---|---|
| exe resource (Explorer, taskbar pin, shortcuts, Apps & features) | `assets/bigwave.ico` via `crates/bwr-app/build.rs` (winresource) |
| window / taskbar at runtime | `assets/bigwave-icon.png` (256 px) |
| tray | `assets/bigwave-icon-64.png` |
| setup + uninstaller exe | `assets/bigwave.ico` (`MUI_ICON` / `MUI_UNICON`) |
| About page logo | `assets/bigwave-logo.png` (wolf icon + wordmark, `scripts/make_branding.py`) |

All come from the wolf pack in `/workspace/loud/pack/BigWave_Radio/` (copied to `assets/icons/`).

`assets/bigwave.ico` is built by `scripts/make_ico.py`: 256 px as PNG, 128/64/48/32/24/16 px as
32-bit BMP with alpha and a matching AND mask. Windows Explorer and Edge often cannot draw
PNG frames at small sizes and show the generic exe/installer icon instead, so never write the
.ico with Pillow's ICO writer (it stores every size as PNG) or copy the pack's all-PNG
`bigwave_radio.ico`. To check a build: `python scripts/check_icons.py assets/bigwave.ico
--exe BigWaveRadio.exe --match --setup BigWaveRadio-<ver>-setup-x64.exe` (needs `pefile`;
the Windows workflow runs this).


## macOS

`.github/workflows/macos.yml` (macos-14; on a `v*` tag push or `workflow_dispatch` with `release_tag`)
runs `scripts/package-macos.sh <ver>`:

1. `cargo build --release` for `aarch64-apple-darwin` and `x86_64-apple-darwin` (`MACOSX_DEPLOYMENT_TARGET=11.0`),
   merged with `lipo` into `BigWave Radio.app/Contents/MacOS/BigWaveRadio`.
2. `Info.plist` from `packaging/macos/Info.plist.in`: bundle id `ie.derekheasley.bigwaveradio`, version from Cargo,
   `LSUIElement` false, icon `assets/BigWaveRadio.icns` (made from the wolf PNG, all sizes incl. Retina).
   No `NSMicrophoneUsageDescription`: the app only plays audio, it never records.
3. Ad-hoc signed (`codesign -s -`, needed for Apple Silicon), not notarised. Users get past Gatekeeper with
   right-click → Open, or `xattr -dr com.apple.quarantine "/Applications/BigWave Radio.app"`.
4. `BigWaveRadio-<ver>-macos-universal.dmg` (hdiutil UDZO: the app, an `Applications` link, `Read me first.txt`)
   and `BigWaveRadio-<ver>-macos-universal.zip` (ditto).

The workflow also runs the tests, `--check-plugin` on every bundled plugin, mounts the dmg, and launches the app for 8 s.

Data: `~/Library/Application Support/BigWaveRadio` (`dirs::data_dir()`). No tray, global hotkey or
media-key integration on macOS yet; closing the window quits.

## Linux

`.github/workflows/linux.yml` builds on **ubuntu-22.04** (x86_64) and **ubuntu-22.04-arm** (aarch64), so the
binaries need glibc 2.35 or newer. `scripts/package-linux.sh <ver>` writes:

| File | Tool | Tested in CI by |
| --- | --- | --- |
| `BigWaveRadio-<ver>-linux-<arch>.tar.gz` | tar | unpack, `--check-plugin`, `install.sh` / `--uninstall` |
| `BigWaveRadio-<ver>-linux-<arch>.deb` | `cargo deb` (`[package.metadata.deb]` in `crates/bwr-app/Cargo.toml`) | `apt install` on Ubuntu 22.04, `--check-plugin`, 8 s launch under Xvfb |
| `BigWaveRadio-<ver>-linux-<arch>.rpm` | `cargo generate-rpm` (`[package.metadata.generate-rpm]`) | `dnf install` in `fedora:latest`, `--check-plugin` |
| `BigWaveRadio-<ver>-linux-<arch>.AppImage` | linuxdeploy (`LINUXDEPLOY=...`) | run with and without `APPIMAGE_EXTRACT_AND_RUN`, `--check-plugin` |
| `BigWaveRadio-<ver>-linux-x86_64.pkg.tar.zst` | `makepkg` on `packaging/arch/bigwave-radio-bin/PKGBUILD` | `pacman -U` in `archlinux:latest`, `--check-plugin` |

All packages install `bigwave-radio`, `bigwave-radio.desktop`, the AppStream metainfo and hicolor icons 16–512 px
(`assets/icons/`, from the wolf pack). `packaging/arch/bigwave-radio/PKGBUILD` builds from the source tag instead
(for the AUR). Data: `$XDG_DATA_HOME/BigWaveRadio` (`dirs::data_local_dir()`). No tray on Linux yet (closing quits);
the Windows-only tray/hotkey/SMTC code is behind `cfg(windows)`.

The update checker picks the asset for the running build: Windows → setup exe, macOS → dmg, Linux → the same
package type it was installed from (AppImage via `$APPIMAGE`, deb/rpm/Arch via `/etc/os-release` when the binary is
under `/usr`, otherwise the tar.gz), and the release page if there's no match.
